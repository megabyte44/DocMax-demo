## "Tell me about your project"

**Q: What is DocMax?**
DocMax is an offline-first, all-in-one document processing CLI published on PyPI. It wraps Tesseract, Ghostscript, Pandoc, and Poppler behind a single terminal interface — a guided TUI for interactive use and a full subcommand API for scripting. It handles 30+ operations: PDF merge/split/compress/encrypt/watermark, OCR, searchable PDF generation, document conversion, content extraction, image preprocessing, multi-threaded batch processing, and watchdog-based folder automation.

**Q: What problem does it solve?**
Most document tools are either cloud-based (privacy risk), GUI-only (not scriptable), or single-purpose. DocMax gives developers and power users one command that covers the full document processing workflow, entirely offline, with clean CLI ergonomics.

**Q: How many users does it have?**
It's published on PyPI. The download badge on the README reflects monthly installs. For exact numbers, I'd check PyPI stats, but the project is live and installable with `pip install docmax`.

## Architecture & Design

**Q: Walk me through the architecture.**
There are four layers: the entry layer (Typer CLI + Questionary TUI menus), the workflow layer (interactive wrappers that prompt for missing params), the core processing layer (single-responsibility modules: engine, operations, processor, converter, extractor, batch, watcher), and the infrastructure layer (utils, config_manager, dependencies). The same core functions power both the CLI and TUI paths — no logic duplication.

**Q: Why is the workflow layer separate from the CLI layer?**
Without it, either the CLI subcommands would contain TUI prompting logic (making them hard to call programmatically) or the TUI would re-implement core logic (causing duplication and divergence bugs). The workflow layer is the bridge — it handles interactive prompting, then calls the same core function the CLI does.

**Q: How does config persistence work?**
Config is stored as flat JSON at `~/.docmax/config.json`. The `config_manager` module provides `get_tool_path()`, `set_tool_path()`, `get_preference()`, `set_preference()`. Every access reads from disk (no in-memory cache) because `docmax setup` can update tool paths mid-session, and a cached value would be stale.

**Q: Why JSON and not SQLite or TOML?**
JSON is read/write with just the Python stdlib. SQLite is overkill for 5 key-value pairs. TOML's stdlib (`tomllib`) is read-only; writes need an extra library. JSON is the simplest option that works cross-platform with no extra dependencies.

## Concurrency & Performance

**Q: How does batch processing work?**
`batch.py` has a `_run_parallel(label, files, workers, handler)` function that wraps `ThreadPoolExecutor`. It submits all files as futures, then iterates `as_completed(futures)` to advance a Rich progress bar. A `workers=1` fast path takes the sequential route with no thread overhead. Errors are collected per-file (non-fatal) and reported at the end.

**Q: Why ThreadPoolExecutor and not ProcessPoolExecutor?**
The operations are I/O-bound — each involves a subprocess call (Tesseract, Ghostscript, Pandoc) and file I/O. Python's GIL doesn't block threads waiting for subprocess exit. Threading works correctly here and avoids the serialization overhead of multiprocessing.

**Q: What's the time complexity of batch OCR?**
O((p/workers) × k × n log n) in the parallel case, where p = files, k = pages per file, n = pixels per page. The n log n factor is Tesseract's internal pipeline cost per image.

**Q: How do you prevent a file being processed twice in watch mode?**
Two mechanisms: a `_seen: set` that is checked and updated atomically before any processing, and a `time.sleep(WATCH_DEBOUNCE_SECONDS)` before the actual processing starts. The set prevents double-dispatch from simultaneous `on_created`/`on_moved` events. The sleep lets file writes settle before DocMax opens the file.

**Q: How do you prevent infinite watch loops?**
DocMax names all output files with known suffixes (`_searchable`, `_compressed`, `_ocr`, etc.). The `dispatch()` method checks `path.stem.endswith(suffix)` for each known suffix and skips the file. This prevents `scan.pdf → scan_searchable.pdf → scan_searchable_searchable.pdf → …`.

## OCR & Document Processing

**Q: How does OCR on a PDF work?**
1. `pdf2image.convert_from_path()` renders each page to a PNG temp file (Poppler backend)
2. Each page image goes through `preprocess_for_ocr()`: enhance (Pillow contrast/sharpness) → deskew (OpenCV Hough transform) → denoise (OpenCV fastNlMeansDenoising)
3. `pytesseract.image_to_string()` runs Tesseract on the preprocessed image
4. Page texts are joined with `---` separators
5. `_write_output()` serializes to TXT, JSON, or Markdown

**Q: How does searchable PDF generation work?**
`pytesseract.image_to_pdf_or_hocr(image, extension="pdf")` produces a PDF page where the original image is the visible layer and Tesseract's recognized text is overlaid as invisible text at the exact pixel coordinates. I collect these per-page PDFs, then merge them with `PdfWriter` from pypdf.

**Q: Why does preprocessing improve OCR accuracy?**
Raw scans fed to Tesseract often have low contrast, skew (physical tilt of the document), and noise (scanner artifacts). Deskewing alone can improve accuracy by 20–40% on tilted scans. Contrast enhancement helps Tesseract distinguish text from background. Denoising removes salt-and-pepper artifacts that confuse character recognition.

**Q: How does document conversion work?**
Via Pandoc subprocess. `convert(input_path, target_fmt)` builds the appropriate Pandoc command (e.g., `pandoc input.md -o output.pdf --pdf-engine=xelatex`) and runs it. I use subprocess instead of `pypandoc` because it gives full CLI flag access and avoids a version-locked binding dependency.

## Error handling & Edge cases

**Q: How do you handle errors in batch processing?**
Each file is wrapped in a `try/except Exception`. Failures are appended to an `errors: list[tuple[Path, str]]` and processing continues. At the end, `_report_errors()` prints a summary. One bad file never aborts the whole batch.

**Q: What happens if a required external tool is missing?**
Each function that depends on an external tool calls a `require_*()` function first (e.g., `require_tesseract()`). This checks `shutil.which(tool)` and the saved config path. If neither finds the tool, it calls `abort()` with a message telling the user to run `docmax setup` or install manually. The error is immediate and descriptive, not a cryptic subprocess failure.

**Q: How do you handle the case where the output path's parent directory doesn't exist?**
`ensure_parent(path)` calls `path.parent.mkdir(parents=True, exist_ok=True)` and is called before every file write. It's used in 14 places. This prevents "No such file or directory" errors when users specify nested output paths.

**Q: What if the user tries to merge a PDF into itself (output == one of the inputs)?**
The `merge()` function writes to a temp file first, then renames. This is the standard safe-overwrite pattern for file operations.

## Extensibility & Future work

**Q: How would you add a new operation (e.g., PDF redaction)?**
1. Add the core function to `operations.py`
2. Add a `cmd_redact()` subcommand in `cli.py`
3. Add a `redact_workflow()` in `workflows/pdf.py`
4. Register it in the PDF menu in `menu.py`
The architecture is additive — no existing code changes needed.

**Q: How would you make DocMax support a GUI?**
The core processing layer (`operations.py`, `engine.py`, etc.) is already decoupled from the TUI. A GUI (e.g., Tkinter or a web app via FastAPI) would just call the same functions, bypassing `cli.py` and `workflows/`. The main change needed is replacing the `abort()`/`success()` console output with return values or exceptions that a GUI can handle.

**Q: How would you scale batch processing for very large folders (10,000+ files)?**
Currently, `collect_files()` loads all paths into memory before starting. For massive folders, I'd switch to a generator-based approach, feeding files into the executor lazily. Also, `as_completed` already processes results as they arrive, so the executor doesn't need all files upfront — just the queue.

**Q: How would you add progress reporting to a headless API?**
Replace the `Rich Progress` calls with a callback function parameter: `_run_parallel(…, on_progress=None)`. Callers pass their own callback (e.g., `lambda completed, total: update_gui(completed/total)`). The Rich progress bar becomes an optional default.

**Q: What would you add next to DocMax?**
1. PDF redaction (black out sensitive regions)
2. Form filling (pypdf supports it)
3. Digital signature verification
4. Better test coverage (currently limited)
5. A `--dry-run` flag for batch operations
6. Async OCR engine for higher throughput

## Behavioral / process questions

**Q: What was the hardest part to build?**
The `make_searchable_pdf` function. The challenge was understanding that Tesseract's `image_to_pdf_or_hocr` in `pdf` mode produces a complete single-page PDF (not just text coordinates), and that I needed to merge these per-page PDFs with `PdfWriter` rather than trying to overlay text on the original PDF directly. Getting the invisible-text overlay correct required understanding how PDF text layers work.

**Q: What bug did you spend the most time on?**
The watch mode infinite loop. Initially, DocMax would watch a folder, compress a PDF, and then immediately detect the compressed output file as a new file to compress — spiraling infinitely. The fix was the output-suffix exclusion list in `dispatch()`. I discovered it by watching the file count in the watched folder grow rapidly in testing.

**Q: What would you do differently?**
Separate extraction from serialization in `extract_tables()` — the current function is too long because it handles both pdfplumber extraction AND CSV/XLSX/JSON output in one place. I'd also add structured logging from the start instead of raw console prints, to make user-reported issues easier to diagnose.

**Q: Why did you publish it to PyPI?**
To make it installable with a single `pip install docmax` — no cloning, no PATH setup, just install and run. Publishing to PyPI also forced me to write proper `pyproject.toml` packaging, optional extras, and an entry point — all good engineering practices.
